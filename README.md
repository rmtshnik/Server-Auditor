# Server Auditor v1.0

Bash-аудитор для Debian, Ubuntu, Linux Mint и Proxmox VE. При запуске без аргументов в терминале открывает меню для аудита и обновления пакетов. Аудит работает в режиме чтения.

[Итоги разработки и дальнейший план](PROJECT_STATUS.md).

[Ревизия кода, ограничения и план упорядочивания меню](AUDIT.md).

## Запуск

Скопируйте каталог на сервер. Для запуска нужны Bash 4+ и стандартные утилиты Linux (GNU coreutils, findutils, awk и инструменты APT/dpkg). Проверки Docker, systemd, ZFS, logrotate и Proxmox используют их локальные утилиты, если они доступны. Для разбора данных о резервных копиях Proxmox нужен Python 3.

```bash
cd server-auditor
bash server-auditor.sh
sudo bash server-auditor.sh menu
sudo bash server-auditor.sh audit --details --lang ru > audit.txt
sudo bash server-auditor.sh audit --format json --lang en > audit.json
```

В меню выберите `1` для сводки, `2` для обновления пакетов, `3` для полного отчёта, `4` для обслуживания или `0` для выхода. В сводке у каждого раздела есть номер, статус и основные показатели. Введите номер, чтобы раскрыть подробности, `s`, чтобы снова увидеть сводку, или `0`, чтобы вернуться в меню. Все разделы показывают результаты одного запуска аудита. В сводку по дискам вынесены показатели корневой файловой системы `/`. Остальные точки монтирования видны в подробностях.

При выборе обновления из меню, открытого обычным пользователем, скрипт вызывает `sudo`, если эта команда доступна. В автоматизации используйте явные команды `audit` и `update --yes`. Запуск без аргументов вне терминала сразу выдаёт краткий текстовый отчёт.

Язык по умолчанию — русский (`--lang ru`). Для английского используйте `--lang en`. Язык применяется к сообщениям аудитора, справке и подтверждениям обновления. Ключи JSON, идентификаторы разделов и коды статусов одинаковы на обоих языках. В отчёте могут встречаться оригинальные термины системных утилит.

Аудит можно запустить от обычного пользователя. Права root дают более полный доступ к журналам, Docker и API Proxmox. Перенаправление вывода создаёт файл с правами вызывающей оболочки. Чтобы ограничить доступ к нему, перед запуском выполните `umask 077`.

## Что попадает в отчёт

| Раздел | Что проверяется |
| --- | --- |
| APT | Состояние dpkg, число удерживаемых пакетов, наличие индексов в стандартном каталоге и симуляция `apt-get upgrade` по уже имеющимся индексам. Если индексы устарели, результат тоже может быть устаревшим. |
| Диски | Общий и доступный объём в байтах, использование блоков и inode на локальных файловых системах. Предупреждение от 85%, критический уровень от 95%. `--details` показывает точки монтирования. |
| Очистка APT | Число и занятое место файлов `.deb` в стандартном кэше, симуляция `apt-get autoremove`, оценка размера пакетов по метаданным dpkg. `--details` показывает пакеты из плана и их размеры. |
| journald | Настройки основного пространства имён на диске с учётом drop-in. Отчёт показывает режим хранения, явные лимиты размера и распознанные параметры резерва и срока хранения. 100 МиБ используется как порог аудита. При отсутствии явного лимита действуют правила systemd по умолчанию. Отдельно измеряется выделенное место под журналы в `/var/log/journal` и `/run/log/journal`. Настройки на диске могут отличаться от уже загруженных службой. |
| logrotate | Пробный запуск конфигурации, число правил, состояние таймера и файлы свыше 100 МиБ в `/var/log` на той же файловой системе, за вычетом каталога journal. `--details` показывает правила ротации из пробного запуска и до 10 крупнейших файлов свыше порога. |
| Docker | Имя, короткий ID и состояние каждого контейнера, параметры ротации логов, образы без тегов и оценка освобождаемого места. Проверяется Docker Engine на `/var/run/docker.sock`. `--details` добавляет пути Compose, подключения файлов хоста и занятое место под текущий `json-file` и его архивы. |
| Ядра | Для установленных ядер отчёт показывает, какие нужно оставить и какие подходят для проверки удаления через меню. Запущенное, самое новое и отдельное запасное ядро с файлами загрузки защищены. Наличие файлов загрузки не подтверждает, что запасное ядро успешно загружалось. Пакеты Proxmox видны в аудите, а меню удаления работает с версионными пакетами `linux-image`. |
| Память и systemd | Занятый и общий объём ОЗУ и подкачки в КиБ, МиБ или ГиБ, процент использования, доступная память и свободная подкачка. ОЗУ считается занятой по разнице между общим объёмом и `MemAvailable`. JSON сохраняет исходные значения в КиБ. В разделе также указано число сбойных юнитов systemd. |
| Proxmox VE | Локальные LXC и их состояние, кворум при видимой конфигурации Corosync, настройки заданий резервного копирования и последние 50 локальных задач `vzdump`. Предупреждение при сбое в этой выборке, отсутствии видимого успешного завершения или возрасте последнего успеха от 7 суток. |
| ZFS | Состояние и заполнение импортированных пулов, в том числе на хостах без Proxmox. |

Статусы `WARN` и `CRIT` отмечают проблемы. `UNKNOWN` означает, что проверку не удалось завершить или однозначно интерпретировать, а `SKIP` отмечает неприменимую проверку. Успешно сформированный отчёт завершает работу с кодом 0 независимо от числа предупреждений. Для автоматической обработки используйте поля `summary` в JSON.

Оба формата показывают имена и короткие ID Docker-контейнеров. Подробный отчёт также содержит нестандартные точки монтирования, имена LXC, пакеты из плана очистки и пути логов. Учитывайте эти данные при передаче отчёта.

### Откуда запущен Docker-контейнер

Для оценки места аудитор берёт путь из `docker inspect` и читает только метаданные файлов драйвера `json-file`. При отсутствии доступа выводится `UNKNOWN`. Другие драйверы могут хранить логи иначе. [Документация драйвера json-file](https://docs.docker.com/engine/logging/drivers/json-file/).

Для контейнеров Docker Compose отчёт с `--details` показывает каталог проекта и файлы конфигурации, если эти сведения записаны в метках контейнера. Это метаданные запуска, поэтому каталог или файлы могли переместиться после создания контейнера. Для обычного `docker run` Docker не хранит каталог, из которого вызвали команду. Подключения типа bind выводятся отдельно как путь на хосте → путь внутри контейнера. [Метки Docker Compose](https://github.com/docker/compose/blob/main/pkg/api/labels.go), [подключение путей хоста в Docker](https://docs.docker.com/engine/storage/bind-mounts/).

## Как читать оценку очистки

Аудит также оценивает ограничения объёма обычных логов по распознанным данным пробного запуска logrotate. В сводке указано число правил с порогом размера, с конечным числом архивов, без обнаруженного порога и с нераспознанными условиями. Подробный отчёт объясняет оценку каждого правила. `minsize` не считается верхним порогом: он запрещает ротацию маленьких файлов. Наличие только временного периода и числа архивов вызывает предупреждение об отсутствии обнаруженного порога размера.

В подробном текстовом отчёте каждое правило показано единым блоком: пути и период, условия, оценка ограничения размера и способ настройки. Для поддерживаемого штатного rsyslog указывается `4 → 3 → 2 → 3`, для редактора стандартных блоков — `4 → 3 → 2 → 2`. Если редактор не поддерживает структуру файла, доступна ручная инструкция `4 → 3 → 2 → 5`. `4 → 3 → 2 → 4` проверяет и запускает существующую конфигурацию, но не меняет её. Номера правил в отчёте не являются номерами пунктов меню. В JSON описание правила остаётся одной строкой.

Общий предел `/var/log` по этим данным не подтверждается. Даже `size` и `maxsize` проверяются при запуске logrotate, шаблоны охватывают переменное число файлов, а некоторые журналы могут обслуживаться другими средствами. Скрипт не выдаёт сумму порогов за гарантированный общий лимит и не меняет настройки при аудите.

В русском отчёте размеры дисков, кэша APT и журналов приводятся в КиБ, МиБ или ГиБ. Подробности logrotate группируются по пронумерованным правилам: список путей и период ротации, затем параметры именно этого правила. Период `after N days` отображается как «период: N сут.». Отчёт показывает распознанные сведения пробного запуска; невыведенный параметр нельзя считать отключённым.

Кэш `.deb` содержит загруженные установочные файлы. Для его очистки можно отдельно выполнить `sudo apt-get clean`. Перед удалением пакетов проверьте свежий план командой `sudo apt-get -s autoremove`. Размер пакетов в отчёте берётся из поля `Installed-Size` и может отличаться от реально освобождённого места. Для ядер проверьте запущенную версию и сохраните рабочее запасное ядро.

Оценка `reclaimable` поступает от Docker. В неё могут входить остановленные контейнеры и тома, которые нужны приложениям или содержат данные. Аудитор оставляет решение об их удалении администратору.

## Обслуживание

В главном меню откройте `4`. Обслуживание сгруппировано по задачам:

```text
1. План освобождения места
2. Пакеты APT и ядра
3. Журналы и ротация
   1. Системный журнал journald
   2. Обычные логи — logrotate
   3. Журналы Docker
   4. Архивы логов
   5. Общая история и восстановление
4. Docker
5. История и восстановление
0. Назад
```

`0` или Enter возвращает на предыдущий экран. Подсказки отчёта содержат полный путь от главного меню. Например, `4 → 3 → 2 → 2` открывает редактор logrotate. Прежняя плоская нумерация из 17 действий заменена этой структурой. Настройка Docker-логов из разделов «Журналы» и «Docker» использует один экран. История внутри раздела журналов пока общая, без фильтра по типу операции.

Пункты `4 → 3 → 1 → 3`, `4 → 3 → 1 → 4` и `4 → 3 → 1 → 2` перед подтверждением показывают текущие настройки journald и его объём. При очистке и настройке постоянного лимита можно выбрать объём в МиБ. Это позволяет отличить разовую ротацию или очистку от постоянного ограничения хранения. Пункт `4 → 3 → 2 → 3` показывает существующее правило rsyslog, распознаёт уже настроенный профиль `daily + maxsize 100M` и позволяет выбрать новые параметры. Если выбранные параметры совпадают с текущими, повторная запись не выполняется. Если штатного правила нет или его структура не поддерживается, изменение не выполняется.

### Выбор объёма и числа файлов

В интерактивном обслуживании можно задать свои значения. Enter выбирает показанное значение по умолчанию, `q` отменяет выбор. Размер вводится целым числом в МиБ от 1 до 1048576, число файлов или архивов — от 1 до 1000.

| Пункт | Что выбирается |
| --- | --- |
| `4 → 3 → 1 → 4` | Целевой общий объём после разовой очистки journald, по умолчанию 100 МиБ. |
| `4 → 3 → 1 → 2` | Постоянный объём journald для каждого из двух хранилищ, по умолчанию 100 МиБ. Количество файлов автоматически определяет journald. |
| `4 → 3 → 2 → 3` | Порог размера одного файла rsyslog и число архивов, по умолчанию 100 МиБ и 4 архива. Текущий файл дополнительно. |
| `4 → 3 → 3 → 2` | Размер одного Docker-лога и общее число файлов на контейнер, по умолчанию 10 МиБ и 3 файла, включая текущий. |

Для маленького сервера можно, например, выбрать 25 МиБ для journald, а для rsyslog — 5 МиБ и 2 архива. Это сокращает доступную историю. Для rsyslog ориентир при таких настройках — 15 МиБ на один путь до учёта сжатия и роста между запусками. Для Docker 2 МиБ и 2 файла дают ориентир 4 МиБ на контейнер. Это разные ограничения, а не единый бюджет журналов сервера.

Для поддерживаемого простого Compose-файла можно изменить и ранее записанные параметры `json-file`. Скрипт сравнивает итоговую конфигурацию и сохраняет копию. Если структура или дополнительные параметры не позволяют безопасно изменить только выбранные лимиты, операция останавливается. Для применения к контейнерам требуется отдельное подтверждение пересоздания.

Аудитор пока сохраняет порог предупреждений 100 МиБ независимо от выбранного лимита. Увеличенный пользовательский лимит поэтому может отмечаться предупреждением аудита.

### Редактор правил logrotate

Откройте `4 → 3 → 2 → 2`. Нужны Python 3, logrotate и права root. Редактор проверяет всю конфигурацию и предлагает блоки из основного файла и стандартного каталога `/etc/logrotate.d/`, которые распознаны как прочитанные logrotate. Если конфигурация невалидна или синтаксис файла не поддерживается, автоматическая запись не предлагается. Дополнительные каталоги include пока не обходятся редактором.

После выбора показываются файл, номер блока, локальные параметры и действующие условия из пробного запуска полной конфигурации. Неуказанные параметры могут наследоваться. Затем можно выбрать:

- порог размера в МиБ;
- число архивов на каждый файл (текущий файл дополнительно);
- ежедневный, еженедельный или ежемесячный период;
- включение, отключение или сохранение текущей настройки сжатия.

Редактор заменяет локальные параметры периода, `size`/`minsize`/`maxsize` и `rotate` выбранными значениями. Другие условия, включая `minage` и `maxage`, сохраняются и могут влиять на ротацию. Команды приложения (`postrotate` и другие), права создания файлов, комментарии вне заменяемых строк и соседние блоки сохраняются. Необычные вложенные или однострочные конструкции отклоняются. Совместимость с конкретным файлом проверяется до записи; наличие файла в списке не гарантирует, что любая его конструкция поддерживается.

Перед подтверждением показывается diff. После подтверждения скрипт создаёт запись истории, сохраняет исходный файл, повторно проверяет его контрольную сумму и записывает только одобренное изменение. Проверка всей конфигурации через `logrotate -d` обязательна. При ошибке скрипт пытается вернуть исходный файл, сохраняя внешние конкурентные изменения. Успешное изменение можно восстановить через `4 → 5 → 2`. Запуск обычной ротации предлагается отдельно, с предварительным планом и собственным подтверждением.

`maxsize` не является общим бюджетом `/var/log` и проверяется при запуске logrotate. Изменение числа архивов может привести к удалению старых журналов при последующих ротациях.

### Инструкция для ручного изменения

Для пошаговой инструкции прямо в скрипте откройте `4 → 3 → 2 → 5`. Выберите существующий конфигурационный файл из списка, посмотрите его содержимое, задайте желаемые размер, число архивов и период. Скрипт покажет, какой файл открыть через `sudoedit`, что заменить внутри нужного блока, какие служебные параметры сохранить и как проверить конфигурацию. Изменения автоматически не записываются. Файл может содержать несколько правил; ориентируйтесь на пути логов внутри блока. Ручные изменения не попадают в историю аудитора автоматически — исходный файл нужно сохранить отдельно вне `/etc/logrotate.d/`.

`4 → 3 → 2 → 4` показывает текущие правила и проверяет ротацию. Этот пункт не меняет настройки. `4 → 3 → 2 → 3` автоматически настраивает только поддерживаемый штатный блок rsyslog.

Для Nginx, UFW и других приложений найдите существующий блок их журналов в `/etc/logrotate.d/`, сохраните резервную копию вне этого каталога и измените нужные параметры внутри блока. Например:

```text
daily
maxsize 100M
rotate 4
compress
```

Это ежедневная ротация, возможность более ранней ротации при превышении 100 МиБ, хранение до четырёх архивов для каждого файла и сжатие архивов. Сохраните необходимые `postrotate`, права создания файлов и другие настройки приложения. Не добавляйте второй блок для тех же путей. Проверьте конфигурацию через `4 → 3 → 2 → 4` до подтверждения запуска. Сначала показывается состояние и план, затем запрашивается подтверждение фактической ротации, если она нужна.

Порог `maxsize` проверяется только при запуске logrotate. У активного таймера нужно учитывать частоту запусков. Эти настройки не создают общий бюджет для `/var/log` и не гарантируют хранение ровно четырёх дней.

Рядом с результатами, для которых предусмотрено действие, выводится подсказка с путём по меню. Например, `4 → 2 → 1` означает «главное меню → обслуживание → пакеты и ядра → очистить кэш APT», а `4 → 4 → 2 → 1` — проверку образов Docker. Подсказка не запускает действие и не подтверждает безопасность удаления. Если настройка не поддерживается, это указано явно. В JSON подсказка доступна в необязательном поле `hint` отдельно от `message`.

В пункте `4` главного меню каждое действие требует подтверждения. При необходимости скрипт вызывает `sudo` после выбора действия.

| Действие | Что происходит |
| --- | --- |
| Очистить кэш APT | Удаляются скачанные архивы пакетов. Установленные пакеты сохраняются. |
| Удалить ненужные зависимости APT | Скрипт показывает свежую симуляцию `autoremove` и после подтверждения заново проверяет список под блокировкой обслуживания. Если в нём есть пакеты ядра, действие останавливается. Удаление выполняется по точному списку зависимостей, с отдельной проверкой и подтверждением. |

Если проверка или перезапуск не проходит, скрипт возвращает прежнюю конфигурацию. Лимит относится к journald. Для текстовых логов приложений действуют их настройки и правила `logrotate`. |

Каталоги должны принадлежать root и быть защищены от записи другими пользователями. Для всех архивов проверяются дескрипторы видимых процессов через `fuser` или, если его нет, через `/proc`. Перед удалением повторно проверяются файл, каталоги, файловая система назначения и содержимое копии. При открытом файле или ошибке проверки оригинал сохраняется. |

| Настроить ротацию обычного syslog | Для штатного блока `/etc/logrotate.d/rsyslog` устанавливает `daily`, выбранный `maxsize` и выбранное число архивов. Сохраняет прежний файл и diff в истории, проверяет полную конфигурацию через `logrotate -d` и откатывает изменение при ошибке. Сжатие и `postrotate` сохраняются. |

| План освобождения места | Выбирает наиболее заполненную локальную файловую систему без учёта Docker overlay. Ищет на ней файлы свыше 10 МиБ и показывает до десяти по занятым блокам. Отмечает активный swap, файлы пакетов, индексы APT, данные контейнеров, архивы и вероятные текущие логи. По номеру подходящего архива можно выбрать перенос с проверкой копии или удаление без копии. Поиск ограничен 30 секундами и отмечает неполный результат. |

После выбора номера скрипт показывает точное имя пакета и запрашивает подтверждение, если симуляция подтверждает удаление только этого пакета. План и результат сохраняются в истории. Наличие файлов загрузки не подтверждает, что запасное ядро уже успешно загружалось. |

При несовместимой структуре файла, других настройках логирования или изменениях за пределами выбранных блоков скрипт останавливается. |
| Восстановить конфигурацию из истории | Показывает до десяти новых успешных изменений journald, rsyslog и Compose. После выбора показывает diff, сверяет контрольные суммы текущего файла и копии и запрашивает подтверждение. При ошибке проверки возвращает конфигурацию, которая была перед восстановлением. |

В плане очистки цвет и текстовая пометка показывают последствия действия. Красный `НЕ УДАЛЯТЬ ВРУЧНУЮ` используется для активного swap, файлов пакетов и данных, обслуживаемых системными утилитами. Зелёный `МОЖНО ОЧИСТИТЬ` отмечает очистку кэша APT и перенос с проверенной копией. Жёлтый `ТРЕБУЕТ ПРОВЕРКИ` отмечает архивы с возможной потерей истории, старые ядра и файлы с неизвестным назначением. Цвет включается только для текстового вывода в терминал. В файлах сохраняются текстовые пометки. Для отключения цвета задайте `NO_COLOR=1`.

История обслуживания и обновлений хранится в `/var/lib/server-auditor/<операция>/history.log`. В записи есть время, вывод команды и статус завершения. После действия скрипт показывает доступное место до и после, а также его изменение для файловых систем, определённых по путям операции. Для переноса архивов учитываются источник и диск назначения, для пакетов — в том числе `/usr` и `/boot`. Повторяющиеся файловые системы объединяются. Раздел, где хранится история, тоже учитывается.

В истории сохраняются поля `space_before_bytes[N]`, `space_after_bytes[N]` и `space_change_bytes[N]` с точными значениями в байтах. Положительное изменение означает рост доступного места, отрицательное — уменьшение. Показатели включают параллельную запись служб и запись самой истории. Если замер недоступен или файловая система сменилась между проверками, разница отмечается как `unknown`. Старые записи доступны через меню истории. Если история не создаётся, действие не запускается. На полностью заполненной файловой системе может понадобиться сначала освободить место вручную.

### Поведение при сбоях

Файл блокировки допускает только одну операцию обслуживания аудитора за раз. Для точечного удаления пакетов скрипт повторяет симуляцию APT и проверку защиты ядер после подтверждения. Если план изменился или запасное ядро исчезло, удаление останавливается. APT также показывает свой окончательный список перед выполнением. Другие программы управления пакетами используют собственные блокировки, поэтому проверьте и этот список.

При изменении конфигураций journald, logrotate и Compose исходный файл сохраняется в истории. Замена и восстановление выполняются через временный файл и переименование. При ошибке проверки или обрабатываемом сигнале завершения скрипт пытается восстановить исходный файл. Если другой процесс уже изменил установленный файл, скрипт сохраняет эту правку и сообщает путь к резервной копии для ручного восстановления. Сигнал `SIGKILL` и отключение питания не позволяют выполнить обработчик отката.

Запись истории синхронизируется перед изменениями и при завершении. Поле `exit_status` хранит результат команды. Поле `recording_status` отдельно отмечает неполную или прерванную историю, что также видно в её меню. При ошибке записи скрипт сообщает об этом и возвращает ненулевой код. Уже выполненное удаление пакетов или архивных записей требует отдельного восстановления из доступных резервных копий.

Скрипт проверяет конфигурацию Compose с основным файлом и при обнаружении файлов без `-f`. После проверки отдельно предлагает применить настройки к выбранным запущенным сервисам. Он запускает `compose up` по одному сервису, проверяет фактические параметры через `docker inspect` и останавливается при ошибке. Сервисы с уже действующими лимитами пропускаются. Compose может кратко прервать работу сервиса при пересоздании. Старый `server-auditor.logging.yml`, если он есть, сохраняется и для будущих запусков после переноса больше не требуется. [Проверка Compose](https://docs.docker.com/reference/cli/docker/compose/config/), [запуск Compose](https://docs.docker.com/reference/cli/docker/compose/up/).

Чтобы вернуть перенесённый архив, проверьте свободное место и скопируйте файл из записанного в истории `backup` обратно в `source`, не перезаписывая существующий файл. Чтобы откатить лимит journald, восстановите сохранённый `journald.conf.before` по пути `dropin`. Если в истории указано `previous=absent`, уберите только созданный аудитором файл. Затем выполните `sudo systemctl restart systemd-journald.service`. История действий не заменяет резервную копию. Записи journald, удалённые при очистке или применении лимита, из истории восстановить нельзя.

Для новых операций меню `4 → 5 → 2` выполняет восстановление конфигурации автоматически. Для этого при изменении сохраняется файл `restore.info` с SHA-256 и данными резервной копии. Если текущий файл менялся после операции или копия повреждена, восстановление останавливается. Старые записи без этих данных доступны для ручного восстановления. Восстановление также записывается в историю с копией заменяемого файла `restore.before`. Для journald перезапускается служба, для rsyslog и Compose проверяется восстановленный файл. Настройки Compose вступят в силу при следующем пересоздании сервисов.

[Команды APT](https://manpages.debian.org/bookworm/apt/apt-get.8.en.html), [ротация и очистка journald](https://manpages.debian.org/bookworm/systemd/journalctl.1.en.html) и [лимиты journald](https://manpages.debian.org/bookworm/systemd/journald.conf.5.en.html).

### Если место занял syslog

Подробный отчёт отмечает крупный текущий `syslog` и его архивы отдельно. Для крупного текущего файла или `syslog.1` после ротации скрипт показывает до пяти самых частых распознанных тегов из последних 20 000 строк. Содержимое сообщений в отчёт не попадает.

```bash
df -h /
sudo fuser -v /var/log/syslog.1
sudo cat /etc/logrotate.d/rsyslog
sudo logrotate -d /etc/logrotate.conf
```

Архив `syslog.1` можно перенести через меню обслуживания после проверки открытых дескрипторов. Для растущего текущего лога сначала проверьте источник записей и правило rsyslog. Порог `maxsize` проверяется во время запуска logrotate, поэтому частота таймера важна. Режим `-d` показывает план ротации без изменений. [Документация logrotate](https://manpages.debian.org/bookworm/logrotate/logrotate.8.en.html).

Через `4 → 1` выберите номер архива, затем `2` для удаления без резервной копии. Скрипт покажет путь, размер и дату изменения. После подтверждения повторно проверит файл и открытые дескрипторы, запишет в историю путь, размер, SHA-256 и намерение удаления. Перед окончательным удалением архив перемещается в закрытый временный каталог на той же файловой системе и проверяется там. При сбое до удаления скрипт пытается вернуть файл. Если исходный путь уже занят, файл сохраняется по указанному в истории `archive_staged_path` для ручного восстановления. После успешного удаления записи архива восстановить из истории невозможно.

## Обновление

```bash
sudo bash server-auditor.sh update
sudo bash server-auditor.sh update --lang en
sudo bash server-auditor.sh update --yes
```

Интерактивный режим требует терминал. Сначала он запрашивает разрешение на обновление индексов, затем показывает симуляцию и запрашивает подтверждение установки. Русские ответы `д` и `да` поддерживаются. Собственный вывод APT идёт в стандартной локали `C`. `--yes` обновляет индексы и запускает установку без вопросов APT, сохраняя локальные конфигурационные файлы в случае конфликтов с пакетами. Ошибка обновления индексов останавливает установку.

В обоих режимах `apt-get upgrade` может устанавливать новые зависимости, но не удаляет пакеты. Пакеты, для обновления которых нужно что-то удалить, могут остаться отложенными. Проверка `autoremove` в аудите выполняется только в режиме симуляции. Установщики пакетов и локальные хуки APT могут перезапускать службы. Если система выставила флаг необходимости перезагрузки, команда выводит уведомление. Терминальный вывод обновления предназначен для локального просмотра и может включать адреса репозиториев или другие сведения из APT.

## Очистка Docker

В меню `4 → 4 → 2` доступны проверка образов и очистка кэша сборки локального Docker Engine. Требуется Python 3. Скрипт обращается к `/var/run/docker.sock` независимо от выбранного Docker context.

Образы показываются с тегами, ID, размером и именами связанных контейнеров. Красным отмечены образы работающих и остановленных контейнеров. Жёлтым отмечены образы без контейнеров — они могут понадобиться для отката. Выберите номер и подтвердите удаление. Перед операцией повторно проверяются связи, теги и метаданные. Образы с несколькими тегами автоматически не удаляются. Используется `image rm --no-prune` без принудительного удаления. Размеры образов включают общие слои, поэтому фактическое освобождение места может быть меньше указанного размера.

Для кэша доступны сроки 7 и 30 дней. Docker удаляет неиспользуемый кэш старше выбранного срока и запрашивает собственное подтверждение. Следующая сборка может занять больше времени. Точный список кэша для предварительного подтверждения Docker Engine не предоставляет. Отдельные Buildx builders, включая удалённые, этим действием не очищаются.

Контейнеры и тома сохраняются. В историю записываются метаданные удаляемого образа или критерий очистки кэша, вывод Docker, код завершения и изменение свободного места. История не содержит резервной копии образов или кэша. Образ для восстановления потребуется загрузить из реестра или собрать заново.
## Тесты

```bash
bash tests/run.sh
```

Тесты проверяют синтаксис обоих файлов, форматы отчёта, меню и вызовы системных утилит через подставные команды. Отдельно проверяются изменение плана APT после подтверждения, исчезновение запасного ядра, открытый архив, несовпадение копии, конкурентная правка конфигурации, прерывание настройки, блокировка обслуживания и ошибка записи истории. При наличии Python 3 проверяются JSON и изменение конфигурации Compose. Тесты не устанавливают пакеты и не требуют root.
