# Server Auditor — итоги и план развития

Состояние на 7 ноября 2026 года. Версия в скрипте — `1.0`.

Этот документ фиксирует цели проекта, реализованные возможности, результаты проверок и порядок следующих работ. Инструкции по запуску и подробное описание команд находятся в [README](README.md).

## 1. Чего мы хотели добиться

Создать один понятный инструмент для аудита и обслуживания серверов на Debian, Ubuntu и Linux Mint. После запуска администратор должен увидеть состояние системы, причины расхода диска и доступные действия по очистке.

Основные требования, сформированные в ходе работы:

- Краткая сводка по разделам с возможностью открыть подробности.
- Русский интерфейс и переключение на английский.
- Понятные единицы размера для дисков, памяти, журналов и кандидатов на очистку.
- Проверка APT, установленных ядер, журналов, Docker и крупных файлов.
- Интерактивное обновление пакетов и обслуживание из одного меню.
- Выбор объектов по номерам, без ручного ввода длинных имён пакетов и контейнеров.
- Явное различие между защищёнными объектами, доступной очисткой и объектами для ручной проверки.
- Предварительная проверка, подтверждение изменений, история действий и возможность восстановления конфигураций.
- Настройка ограничений журналов, чтобы после очистки проблема не возникала снова.

К проекту также добавлены проверки Proxmox VE и ZFS. Их реальную совместимость предстоит подтвердить отдельно.

## 2. Что уже сделано

### Отчёт и интерфейс

Реализованы интерактивное меню, краткая сводка с раскрытием разделов, полный текстовый отчёт и JSON. Сводка и подробности относятся к одному запуску аудита. Аудит выполняет проверки без изменения настроек системы.

Русский язык используется по умолчанию, английский включается через `--lang en`. Ключи JSON и коды статусов остаются одинаковыми на обоих языках. Сообщения внешних утилит могут выводиться на их исходном языке.

Объёмы отображаются в КиБ, МиБ и ГиБ. Для ОЗУ и подкачки показаны использование и доступный остаток. Цветовые обозначения сопровождаются текстом, поэтому смысл сохраняется при записи отчёта в файл:

| Обозначение | Значение |
| --- | --- |
| Красный — «НЕ УДАЛЯТЬ ВРУЧНУЮ» | Защищённый объект или данные, которые нужно обслуживать штатными средствами. |
| Зелёный — «МОЖНО ОЧИСТИТЬ» | Предусмотренная операция очистки, например кэша скачанных пакетов, или перенос с проверенной копией. |
| Жёлтый — «ТРЕБУЕТ ПРОВЕРКИ» | Необходимо оценить последствия: потерю архивных записей, возможность отката или назначение файла. |

| Направление | Реализовано |

| Память | Общая, занятая и доступная ОЗУ, объём и использование подкачки. |
| APT | Проверка dpkg, удерживаемых пакетов, плана обновления по имеющимся индексам, кэша и кандидатов autoremove. |
| Ядра | Установленные версии, запущенное ядро, защищённые версии и кандидаты на проверку удаления. |
| journald | Режим хранения, настройки лимитов, фактически занятое место. |
| Обычные логи | Пробный запуск logrotate, состояние таймера, крупные файлы в `/var/log`. |
| Источники syslog | До пяти наиболее частых распознанных тегов в выборке последних 20 000 строк крупного syslog или его первого архива. |

### Обновление и пакеты

Добавлено обновление индексов APT, предварительная симуляция и подтверждение установки. Обновление выполняется с запретом удаления пакетов. Предусмотрен явный режим `update --yes` для автоматизации.

Кэш скачанных пакетов очищается отдельно. Удаление ненужных зависимостей выполняется по проверенному точному списку. При наличии пакетов ядра в общем плане autoremove действие блокируется и предлагается отдельная проверка ядер.

### Ядра

Защищены запущенное ядро, самое новое установленное ядро и отдельное запасное ядро с файлами загрузки. Когда эти роли совпадают, число защищённых версий может быть меньше трёх. Наличие файлов загрузки само по себе не подтверждает успешную загрузку запасного ядра.

Старый пакет `linux-image` выбирается по номеру. Перед удалением проверяется симуляция APT и соответствие точного списка выбранному пакету. После подтверждения проверка повторяется.

Для Ubuntu добавлена отдельная очистка связанных модулей, заголовков и инструментов по версии уже удалённого ядра. Она также выполняется по выбранной нумерованной группе и проверенному плану APT.

### Журналы и предотвращение повторного роста

- Ротация активных файлов journald.
- Разовая очистка архивов journald с целевым размером 100 МиБ.
- Постоянные лимиты journald через отдельный drop-in.
- Настройка штатного правила rsyslog на `daily` и `maxsize 100M` с сохранением остальных поддерживаемых параметров.
- Показ плана logrotate и запуск обычной ротации по действующим правилам.
- Сохранение исходных конфигураций, проверка изменений и обработка ошибок.

Порог `maxsize` проверяется при запуске logrotate. Он не гарантирует, что файл никогда не превысит 100 МиБ между запусками. Снижение избыточного потока сообщений конкретного приложения остаётся отдельной задачей.

### Крупные файлы и архивы логов

План освобождения места выбирает наиболее заполненную локальную файловую систему и показывает до десяти крупнейших файлов свыше 10 МиБ по занятым блокам. Поиск ограничен по времени. Отдельно распознаются активный swap, файлы пакетов, индексы APT, данные контейнеров, текущие логи и подходящие архивы.

Для поддерживаемого архива доступны перенос на другую файловую систему с проверкой копии и удаление без резервной копии с явным подтверждением. Перед операцией проверяются путь, тип файла, открытые дескрипторы и неизменность объекта.

При удалении архив сначала перемещается в закрытый временный каталог на той же файловой системе и повторно проверяется. При сбое до окончательного удаления предусмотрена попытка возврата. Если исходный путь уже занят новым файлом, сохранённый архив оставляется для ручного восстановления.

Произвольное удаление любого крупного файла из списка не реализовано. Для текущего syslog предусмотрено обслуживание через logrotate и отдельная работа с получившимся архивом.

### Docker и Compose

Контейнеры показываются по именам с дополнительным коротким ID. Для Compose используются метки проекта, позволяющие определить каталог запуска и конфигурационные файлы. Для обычного `docker run` исходный рабочий каталог Docker не хранит.

Для выбранных по номерам контейнеров одного проекта можно записать ограничения `json-file` размером `10m × 3` непосредственно в основной Compose-файл. Поддерживаемая структура проверяется консервативно, исходный файл сохраняется, итоговая конфигурация сравнивается средствами Compose.

После сохранения можно отдельно подтвердить применение настроек. Скрипт при необходимости пересоздаёт сервисы по одному и проверяет фактические параметры контейнеров. Уже действующие лимиты повторно не применяются. Основной файл сохраняет настройки для последующих обычных запусков Compose.

Добавлен этап **«Очистка Docker»**, пункт `4 → 15`:

- Список образов с тегами, полным ID для выбранного объекта, размером и связями с контейнерами.
- Защита образов работающих и остановленных контейнеров.
- Выбор неиспользуемого образа по номеру и подтверждение удаления.
- Повторная проверка метаданных и связей перед удалением по неизменяемому ID.
- Удаление без принуждения и без автоматической очистки родительских образов.
- Блокировка автоматического удаления образов с несколькими тегами.
- Очистка неиспользуемого кэша встроенного builder Docker Engine старше 7 или 30 дней с подтверждением Docker.
- Запись результата и изменения свободного места в историю.

Контейнеры и тома этим этапом не удаляются. Отдельные Buildx builders пока не обслуживаются. Размеры образов включают общие слои и не равны гарантированно освобождаемому месту.

### История и восстановление

История хранится в `/var/lib/server-auditor`. В записи сохраняются тип операции, время UTC, параметры действия, вывод команд, статус завершения и измерение свободного места до и после операции. Ошибки записи истории отмечаются отдельно.

Изменения конфигураций journald, rsyslog и Compose сопровождаются резервными копиями. Для новых записей предусмотрено восстановление по номеру с проверкой SHA-256, показом diff и сохранением заменяемой конфигурации.

Обслуживание защищено общей блокировкой аудитора. При изменениях файлов проверяются права каталогов, символические ссылки и конкурентные изменения. Для ряда операций предусмотрены обработчики прерывания и отката.

История не является резервной копией удалённых данных. Она не восстанавливает удалённые записи логов, образы Docker или пакеты. Принудительное завершение `SIGKILL` и отключение питания не позволяют выполнить обработчик отката.

## 3. Что уже проверено

### Локальные автоматические проверки

Последний полный запуск `tests/run.sh` завершился успешно. После уточнения заглушек дополнительно прошли новые сценарии Docker.

Проверки используют подставные системные команды. Они охватывают синтаксис, форматы отчёта, меню, проверки планов APT, защиту ядер, работу с архивами, конфигурациями и историей. Для Docker проверены защита образа остановленного контейнера, изменение тегов после выбора, удаление выбранного образа, допустимые сроки очистки кэша и отмена действий.

Это проверка логики скрипта. Она не заменяет запуск с реальными версиями Docker, APT, systemd и файловыми системами.

### Проверки пользователя на серверах

| Среда или операция | Подтверждённый результат по присланному выводу |
| --- | --- |
| Debian — удаление старого ядра | Удалён выбранный старый пакет, обновлена конфигурация GRUB, операция завершилась с кодом 0. |
| Ubuntu — удаление старого ядра | Удалён выбранный `linux-image`, рабочее и запасное ядра остались в конфигурации загрузки, код завершения 0. |
| Ubuntu — связанные пакеты ядра | Удалена выбранная группа headers/modules/tools, код завершения 0. |
| История обслуживания | Проверены список последних операций и открытие записи по номеру. |
| Docker Compose | Для двух сервисов применены и проверены фактические лимиты `json-file` `10m × 3`. |
| Основной Compose-файл | Лимиты записаны в основной файл, повторная проверка обнаружила уже действующие настройки. |
| Удаление архива syslog | Удалён выбранный архив размером около 69,8 МиБ, показано соответствующее изменение доступного места. |
| План освобождения места | Проверены крупные файлы, распознавание активного swap и файлов пакетов на сервере пользователя. |

В ходе диагностики отдельно выявлен значительный поток сообщений от `warp-svc`. Настройки ротации ограничивают хранение, но причина такого потока требует проверки самого сервиса.

В последних присланных планах заполнение корневого раздела Debian-сервера снизилось до 78% с доступными примерно 2,10 ГиБ до дополнительного удаления архива. Это наблюдение по разным моментам времени, а не точный суммарный результат одного запуска очистки. Часть первых действий выполнялась вручную.

Ниже приведён обновлённый план. Будущие возможности не считаются реализованными до проверки кода и результатов запуска.

| 2 | Завершить проверку совместимости | Linux Mint, уточнение версий Debian/Ubuntu, проверка русской и английской локализации в реальном терминале. |
| 3 | Проверить отложенные операции восстановления | Перенос архива на другой диск, сверка копии, восстановление конфигураций на тестовой системе. |
| 4 | Расширить поддержку Buildx | Обнаружение builders, указание драйвера и endpoint, обзор кэша, отдельная подтверждаемая очистка проверенного локального builder. |
| 5 | Улучшить диагностику быстрого роста логов | Более наглядный отчёт по источникам сообщений и объяснение связи между скоростью записи, порогом размера и частотой ротации. |
| 6 | Проверить Proxmox VE и ZFS | Отдельная матрица реальных проверок с фиксацией версий и ограничений. |
| 7 | Подготовить публикацию и выпуск | Репозиторий GitHub, согласованная версия, проверяемый набор файлов, лицензия, проверки CI и описание выпуска. |

### Этап 1. Приёмка очистки Docker

На тестовом сервере нужно подтвердить следующие сценарии:

1. Образы работающего и остановленного контейнера защищены.
2. Неиспользуемый образ с одним тегом удаляется после выбора и подтверждения.
3. Образ с несколькими тегами не предлагается к автоматическому удалению.
4. Отмена выбора и подтверждения сохраняет объекты.
5. Изменение связей или тегов после выбора останавливает действие, когда оно обнаружено повторной проверкой.
6. Очистка кэша за выбранный срок завершается штатно и попадает в историю.
7. Замеры места отображаются корректно, включая отдельный раздел данных Docker при его наличии.

### Этап 2. Совместимость и восстановление

Проверка Linux Mint отложена по договорённости. Перенос архивов на другой диск также отложен, поскольку отдельного диска сейчас нет.

Для этих этапов нужно записать версии ОС и утилит, ожидаемый результат и фактический вывод. Восстановление конфигураций следует проверить как при неизменённом текущем файле, так и после внешней правки — во втором случае скрипт должен отказаться от автоматической замены.

### Этап 3. Buildx

Встроенный builder Docker Engine и отдельные Buildx builders нужно показывать раздельно. Перед добавлением очистки требуется надёжно определить endpoint и исключить случайное обслуживание удалённого builder.

Обзор кэша должен показывать, к какому builder относится оценка. Для удаления нужны отдельное подтверждение, критерий возраста, история и понятное описание ограничений предварительного просмотра.

### Этап 4. Подготовка к GitHub

1. Проверить состав файлов и diff перед первым коммитом.
2. Определить репозиторий назначения и подключить remote, если он отсутствует.
3. Определить лицензию проекта и добавить соответствующий файл.
4. Добавить CI для синтаксиса Bash, тестов и статического анализа, если его результаты будут разобраны.
5. Указать проверенные версии ОС и отделить их от заявленных целевых платформ.
6. Согласовать номер первого публикуемого выпуска, подготовить описание и выполнить коммит и push.

Репозиторий проекта — [rmtshnik/Server-Auditor](https://github.com/rmtshnik/Server-Auditor), Git remote — `origin`, основная ветка — `main`. Исходники, тесты и документация публикуются в этой ветке. Отдельный тег и GitHub Release пока не созданы.

## 5. Критерии готовности первого проверенного выпуска

- На проверенных Debian, Ubuntu и Linux Mint корректно работают аудит, сводка и меню.
- Удаление ядер сохраняет защищённые версии и останавливается при изменении плана.
- Текущие логи обслуживаются штатной ротацией, удаление архивов требует отдельного подтверждения.
- Лимиты journald и Compose сохраняются, валидируются и доступны для восстановления из новых записей истории.
- Новая очистка Docker подтверждена на реальном сервере.
- Основные отказы и отмены покрыты локальными тестами.
- README содержит ограничения, зависимости, инструкции запуска и проверенные платформы.
- В GitHub опубликованы исходный код, тесты, документация и сведения о лицензии.
